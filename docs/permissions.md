# 权限模型与分享链接

权限与分享决定“谁可以对这个资源做什么”。本文件是权限级别、权限检查点、权限继承、权限表与分享链接表和分享访问校验的唯一说明。

本文件说明权限级别、权限检查点、权限继承、权限表与分享链接表的规则以及分享访问校验；表中各字段的精确定义以 `data-model.md` 为准。端点与错误码见 `api.md`，安全红线（前端隐藏按钮不算权限控制、分享 Token 只存哈希、管理员访问必须留审计）见项目根 `AGENTS.md` 第 8 节与 `security.md`。

## 1. 权限级别

系统定义四种权限级别：

```text
READ
WRITE
OWNER
ADMIN
```

含义：

| 权限 | 含义 |
|---|---|
| `READ` | 查看目录、读取文件、下载文件。 |
| `WRITE` | 包含 READ，并允许上传、更新、移动、重命名和删除。 |
| `OWNER` | 管理资源权限、分享链接和删除资源。 |
| `ADMIN` | 管理用户、系统配置和全局资源。 |

说明：

- `WRITE` **包含** `READ`，不需要为同一个用户再单独授予 `READ`。
- `OWNER` 是资源级权限，负责该资源的权限管理与分享链接。
- `ADMIN` 是系统级权限，拥有全局管理权限；管理员访问用户文件时仍然必须记录审计日志。

分享链接上的权限值只有只读与可写两种取值（见第 6 节），完整的四级权限用于用户对资源的授权关系。

## 2. 权限检查原则

**所有权限必须在服务端检查。前端隐藏按钮不是权限控制。**

权限检查必须覆盖以下 13 个检查点：

| # | 检查点 |
|---|---|
| 1 | 查看目录。 |
| 2 | 获取文件元数据。 |
| 3 | 下载文件。 |
| 4 | 初始化上传。 |
| 5 | 上传分块。 |
| 6 | 完成上传。 |
| 7 | 删除文件。 |
| 8 | 恢复文件。 |
| 9 | 移动文件。 |
| 10 | 创建分享链接。 |
| 11 | 修改权限。 |
| 12 | 查看版本。 |
| 13 | 下载历史版本。 |

要求：

- 检查点不能只覆盖“进入页面”一级；上表中每一行都是独立的资源级判定。
- 检查必须落到具体资源（文件夹、文件、版本、上传会话、分享链接）上，而不是只判断“是否已登录”。
- 公开分享接口不需要登录态，但同样必须在服务端校验分享链接本身（见第 7 节）。
- 任何权限校验失败都必须返回统一的权限错误码，具体错误码见 `api.md`。

### 2.1 管理员的安全边界

- 管理员拥有全局管理权限，但**管理员访问用户文件时仍然必须记录审计日志**。
- 管理员不能在没有审计记录的情况下静默读取用户文件。
- 管理员操作必须可追溯；管理员页面的能力范围与管理 API 分组见 `architecture.md`，本文件只约束其安全面。

## 3. 权限继承

MVP 采用的继承规则：

- 文件默认继承所属文件夹的访问权限。
- 文件可以拥有额外权限。
- 删除文件夹前必须处理继承关系。
- 权限查询结果必须可预测。

约束：

- 权限继承规则必须写入文档（即本节），不允许只存在于实现里。
- **不要在第一版实现复杂的拒绝权限、组嵌套和 ACL 优先级系统。**
- 继承关系在删除文件夹时必须先被处理，不能留下指向已删除文件夹的悬空授权。

### 3.1 阶段九的实现算法（权威）

判定某个用户对某个资源的**有效级别**时，按顺序：

```text
1. 未登录（actor 为空）                         → 拒绝
2. actor 角色是 ADMIN                           → 允许（调用方必须写审计）
3. actor 就是资源所有者（folders/files.owner_id） → OWNER
4. 资源自身的授权记录（permissions 表）          → 该级别
5. 祖先文件夹的授权（含文件所在目录自身）         → 路径上**最高**的那一级
6. 都没有                                       → 拒绝
```

- **祖先**怎么找：文件夹用 materialized path（`folders.path_key` 形如 `/a/b/c/`），
  目标目录的 path_key 是祖先 path_key 的延续，因此一条 `$path LIKE path_key || '%'`
  就能取出整条路径上的授权（阶段三就为此建好了结构）。
- **取最高不取最近**：路径上同时有 READ 与 WRITE 时结果是 WRITE。
  第一版**没有拒绝规则**，所以不存在"下层覆盖上层"的语义。
- 只统计 **ACTIVE** 的文件夹：已删除目录上的旧授权不再生效，避免用删除状态绕过。
- 删除**永久**删除资源时会清理授权：删目录时连同子树的授权与分享链接一起删，
  不留悬空记录（软删除不动授权，因为恢复后还要用）。

### 3.2 动作与所需级别

| 动作（`ResourceAction`） | 覆盖的操作 | 所需级别 |
|---|---|---|
| `kRead` | 查看目录、读元数据、下载、查看/下载历史版本 | READ |
| `kWrite` | 上传（初始化/分块/完成）、改版本、移动、重命名 | WRITE |
| `kDelete` | 软删除（进回收站） | WRITE |
| `kManage` | 永久删除、改权限、创建/撤销分享链接 | OWNER |

> `WRITE` 包含 `READ`，不需要重复授予。永久删除与权限/分享管理按 `OWNER` 把关，
> 因为它们会改变"其他人能看到什么"，比改内容更敏感。

### 3.3 共享目录里的文件归属

被授权的协作者上传文件时：

- 上传会话属于**上传者**（这样协作者能查询状态、续传、取消自己的上传）。
- 生成的文件与版本归属**目录所有者**（`files.owner_id` / 新版本的 `created_by` 记上传者），
  配额也记在目录所有者名下。协作者不会因为帮别人上传而占用自己的配额。

## 4. Permission（资源权限表）

`permissions` 表的字段定义见 [data-model.md](data-model.md)，此处不重复。

初版支持的授权组合：

```text
subject_type = USER
permission = READ | WRITE | OWNER
```

写入规则：

- `subject_type` 初版只支持用户级权限，取 `USER`；`permission` 取 `READ` / `WRITE` / `OWNER`。
- 一条记录表示“某个用户对某个资源拥有某个权限”。
- 资源的 `OWNER` 是对应 `permission = OWNER` 的授权记录，不是独立字段。
- 管理员通过 `ADMIN` 级别获得全局管理权限，不需要为每个资源单独插入记录。
- 管理员访问用户资源的动作必须留下审计日志，不得静默读取。
- 具体的权限查询、授予、删除端点与请求体见 `api.md`。

## 5. ShareLink（分享链接表）

`share_links` 表中各字段的名称与定义见 [data-model.md](data-model.md)，此处不重复。字段在权限与分享语义上的作用如下：

- `permission`：分享权限，只读或可写。
- `expires_at`：过期时间，为空表示不自动过期。
- `max_downloads` 与 `download_count`：允许的最大下载次数与已发生的下载次数，两者比较后决定是否达到下载次数。
- `revoked_at`：撤销时间；为空表示未撤销。
- `created_by` / `created_at`：创建者与创建时间。

**分享链接只保存 Token 的哈希值，不保存明文 Token。**

- `token_hash` 使用 SHA-256；数据库中没有明文 Token 列，服务端也不保存明文。
- 分享 Token 必须使用高强度随机值。
- 明文 Token 只在创建时返回一次，之后无法再取回。
- 分享链接的外部访问是一次 Token 查找：用请求携带的明文 Token 计算 SHA-256 后按 `token_hash` 匹配记录。

## 6. 分享访问校验

### 6.0 阶段九的实现（权威）

| 环节 | 实现 |
|---|---|
| Token 生成 | OpenSSL `RAND_bytes` 32 字节（256 位）→ base64url，43 个字符 |
| Token 存储 | 只存 `SHA-256(明文)`；数据库没有明文列，服务端也不缓存明文 |
| 明文返回 | 只在 `POST /resources/{id}/shares` 的响应里出现一次，之后无法再取回 |
| 访问校验 | 一条 SQL 过滤掉撤销与过期的记录，**不降级放行** |
| 下载计数 | `UPDATE ... WHERE download_count < max_downloads RETURNING`，一条语句完成"检查 + 计数"，并发下载不会同时通过 |
| 资源绑定 | 分享只作用于它绑定的那一个 `resource_id`，下载时按该 id 解析资源 |
| 目录分享 | 可以查看（列出名字/大小/权限），**不支持打包下载**，返回 `403` 并给出原因 |
| 错误语义 | 过期 / 撤销 / 超次 / Token 不存在统一返回 `404 RESOURCE_NOT_FOUND`，不泄露具体原因 |
| 响应头 | 公开下载带 `X-Robots-Tag: noindex` 与 `Cache-Control: no-store` |
| 审计 | 创建与撤销分享都写 `audit_logs`（含操作者与资源） |

分享链接访问必须支持以下 5 项判断：

| # | 判断 | 依据字段 |
|---|---|---|
| 1 | 是否过期。 | `expires_at` |
| 2 | 是否被撤销。 | `revoked_at` |
| 3 | 是否达到下载次数。 | `max_downloads` 与 `download_count` |
| 4 | 是否允许下载文件夹。 | `resource_type`（文件夹分享的下载允许性） |
| 5 | 是否需要密码。 | 密码分享相关字段 |

补充要求：

- **密码分享属于可选功能，不纳入最小 MVP。** 第 5 项判断保留为接口与模型上的位置，第一版不实现密码分享流程。
- 分享链接只对它绑定的那一个资源生效，必须防止分享链接越权访问其他资源。
- 过期、被撤销、超出下载次数的分享 Token 一律拒绝下载，不允许降级放行。
- 公开分享的查看与下载接口不要求登录，但校验逻辑必须与其他资源访问一样在服务端执行。

## 7. 前端分享交互要点

分享弹窗支持：

- 创建分享链接。
- 选择只读或可写。
- 设置过期时间。
- 复制链接。
- 撤销链接。
- 查看访问次数。

Token 展示规则：

- 创建成功后只能向用户展示一次明文 Token，服务端不保存明文 Token。
- 创建结果展示之后无法再次查看同一 Token；需要新 Token 只能重新创建分享链接。
- 分享弹窗同样不能把“隐藏了按钮”当作权限控制，能否创建、修改、撤销分享链接最终由后端判定。
