# 删除恢复、故障处置、后台任务与备份

删除策略：**软删除 + 后台永久清理**。

## 1. 删除与恢复

### 1.0 阶段八实现现状（行为以此为准）

| 操作 | 接口 | 数据库 | 磁盘对象 | 配额 |
|---|---|---|---|---|
| 软删除文件 | `DELETE /api/v1/files/{id}` | `status='TRASHED'` + `deleted_at` | **不动** | 仍占用 |
| 软删除文件夹 | `DELETE /api/v1/folders/{id}` | 整棵子树的文件夹**和其中的文件**都置 `TRASHED` | 不动 | 仍占用 |
| 回收站列表 | `GET /api/v1/trash` | 文件与文件夹合并成一张清单，支持按类型筛选与分页 | — | — |
| 恢复 | `POST /api/v1/trash/{id}/restore` | 置回 `ACTIVE`；文件夹恢复整棵子树 | 不动 | 不变 |
| 永久删除 | `DELETE /api/v1/trash/{id}/purge` | 事务内删记录、回收配额 | **不在请求里删**，写 `cleanup_tasks` | 释放 |

恢复的三条规则：

1. **幂等**：重复恢复返回 200 并标记 `already_restored`（资源已经是 `ACTIVE`）。
2. **父目录不在则回到根目录**：原父目录被删或不再是 `ACTIVE` 时，文件落到用户根目录，
   响应里 `moved_to_root: true`，前端会明确提示。
3. **同名冲突则拒绝**：目标目录下已有同名资源时返回 `409 RESOURCE_CONFLICT`，
   `details.conflict_name` 给出冲突者，**不改动任何状态**。

删除后的可见性：`TRASHED` 的资源不出现在目录列表、不能读元数据、不能下载、不能看版本、
不能作为新版本的目标——统一返回 `404`，避免用删除状态做存在性探测。

删除分为两类：

```text
软删除
永久删除
```

### 1.1 软删除

软删除时必须完成 5 件事：

| # | 要求 |
|---|---|
| 1 | 更新资源状态为 `TRASHED` |
| 2 | 设置 `deleted_at` |
| 3 | 普通文件列表不再显示该资源 |
| 4 | 文件内容暂时保留 |
| 5 | 记录操作者和删除时间 |

### 1.2 恢复

| 场景 | 处置 |
|---|---|
| 原父目录仍存在 | 恢复到原父目录下 |
| 原父目录已不存在 | 恢复到用户根目录 |
| 目标位置同名冲突 | 拒绝恢复并返回冲突信息，或生成可配置的新名称 |

- 恢复前必须检查原父目录是否仍存在。
- 恢复操作必须幂等。
- 恢复冲突的用户侧提示见 [frontend.md](frontend.md)；恢复接口与错误码见 [api.md](api.md)。

### 1.3 永久删除

永久删除前必须：

- 检查权限。
- 检查资源状态。
- 删除数据库引用。
- 异步删除对象存储内容。
- 记录清理任务。
- 删除失败时必须可重试。

**不允许在 HTTP 请求中长时间同步删除大量目录树。**

## 2. 故障场景与处置

### 2.1 网络中断

处理流程：

1. 当前分块失败。
2. 保留上传会话。
3. 前端显示“等待网络恢复”。
4. 网络恢复后查询上传状态。
5. 只上传后端返回的缺失分块。
6. 达到最大重试次数后允许手动重试。

前端的等待提示、可重试错误分类与重试时序见 [frontend.md](frontend.md)。

### 2.2 后端重启

后端重启后：

- PostgreSQL 中的上传会话仍然存在。
- 已上传分块记录仍然存在。
- Redis 缓存丢失时，从 PostgreSQL 恢复状态。
- 后台清理任务重新扫描过期会话。
- 正在合并的会话必须能够判断临时文件是否完整。
- 不允许把所有 `UPLOADING` 会话直接标记为失败。

**阶段五的实现现状**（`upload_sessions` / `upload_chunks` 是唯一事实来源）：

- 会话与分块状态全部落 PostgreSQL，Redis 不参与断点续传，因此重启后 `GET /api/v1/uploads/{id}` 仍能返回真实的 `completed_chunks`。
- 分块直接落盘在 `storage/tmp/uploads/<upload_id>/<index>`，重启不会丢失已传分块。
- 合并过程把分块拼进 `tmp/<uuid>` 临时对象，算出 SHA-256 后才 `Commit` 到内容寻址的最终 key；进程在合并中途被杀只会留下一个无引用的 `tmp/` 文件，由后台清理任务回收（阶段十一）。
- 重启时停在 `MERGING` 状态的会话不会自动失败：重新调用 `complete` 会重新合并（`ClaimForMerge` 只允许一次抢占，需要人工或后台把卡住的会话放回可重试状态，见阶段十一的清理任务）。

### 2.3 Redis 重启

Redis 只保存缓存和短期状态。

Redis 不可用时：

- 登录和上传状态查询不能完全依赖 Redis。
- 对必须依赖 Redis 的功能返回可识别错误。
- 不允许静默跳过权限、限流或锁。
- Redis 恢复后业务可以继续执行。

Redis 保存的内容边界见 [architecture.md](architecture.md)。

### 2.4 PostgreSQL 不可用

- 新上传初始化失败。
- 文件元数据变更失败。
- 已经上传到临时目录但未提交的数据进入待清理状态。
- API 返回 `STORAGE_UNAVAILABLE` 或数据库相关错误。
- 不得向用户返回成功响应。

### 2.5 磁盘空间不足

- 上传初始化阶段检查可用空间。
- 每个分块写入前再次检查。
- 失败后上传会话标记为 `FAILED` 或保留为可重试状态。
- 返回 `STORAGE_FULL`。
- 管理员页面显示磁盘使用情况。

### 2.6 上传会话过期、失败与清理

会话有效期默认 24 小时（`UPLOAD_SESSION_TTL`，范围 60 秒 ~ 30 天）。**过期时间由数据库用
`now() + make_interval(secs => $N)` 计算**，避免客户端或应用进程的时钟偏差影响判定。

读会话时（`FindById`）会顺带把已过期且仍在 `INITIATED`/`UPLOADING` 的会话落成 `EXPIRED`，
后续分块上传返回 `410 UPLOAD_EXPIRED`，`complete` 同样被拒。这样即使后台清理任务没跑，
过期会话也不会被继续写入。

失败与结束时的资源回收（`UploadService::Complete` / `Cancel`）：

| 场景 | 会话状态 | 数据库分块 | 磁盘分块 | 临时对象 |
|---|---|---|---|---|
| 正常完成 | `COMPLETED` | 随事务删除 | 删除整个 `tmp/uploads/<id>/` | 提交到 `objects/<xx>/<hash>` |
| 分块不齐（`UPLOAD_INCOMPLETE`） | 保持可续传 | 保留 | 保留 | 无 |
| 哈希不匹配 / 大小不符 / 合并失败 | `FAILED` | 删除 | 删除 | 删除临时文件 |
| 客户端取消 | `ABORTED` | 删除 | 删除 | 无 |
| 会话过期 | `EXPIRED` | 由清理任务回收 | 由清理任务回收 | — |

> 只删数据库记录而留下磁盘分块会让失败的上传一直占着空间，因此失败路径统一走
> `fail_upload()`：**磁盘分块、分块记录、会话状态一起收尾**。

并发处理：`ClaimForMerge` 用一条 compare-and-set 语句把会话从 `INITIATED`/`UPLOADING`
推进到 `MERGING`，只有抢到的请求会去合并，其余并发请求得到 `409 RESOURCE_CONFLICT`
（若前者已经完成，则幂等返回同一个文件）。**合并过程不持有数据库锁。**

### 2.7 版本回退与误改恢复

内容被改坏时用版本历史回退，**不需要从备份恢复**：

| 场景 | 做法 | 结果 |
|---|---|---|
| 新版本内容有问题 | `POST /files/{id}/versions/{vid}/restore` | 追加一个内容等于旧版本的新版本，当前内容回到旧版本 |
| 想找回被覆盖的内容 | `GET /files/{id}/versions/{vid}/download` | 拿到该版本的原始字节 |
| 恢复后发现有误 | 再恢复到另一个版本 | 双向可回退，任何历史版本都不会被删除 |
| 重复点击恢复 | 幂等 | 当前内容已等于目标版本时不追加新版本 |

关键性质（阶段七实现，已有集成测试与端到端测试覆盖）：

- **只增不减**：版本号 = 当前最大 + 1；`file_versions` 的旧版本行与磁盘对象都保留，
  只有删除文件记录才会级联删除版本行（阶段八的永久删除）。
- **旧对象不被覆盖**：每个版本有自己的内容寻址 `storage_key`，新版本不会覆写当前版本的对象。
- **恢复也占配额**：历史版本与恢复产生的新版本都计入 `used_storage_bytes`。
- **冲突可解释**：并发修改用 `If-Match` 判定，冲突返回 `409 FILE_VERSION_CONFLICT`，
  `details.current_version_id` 给出真实当前版本，客户端刷新后重试即可。
- 数据库有记录但磁盘对象缺失时，恢复会拒绝并写错误日志，不会写出指向空内容的版本。

## 3. 后台任务与清理

### 3.0 阶段八已实现的后台清理

`CleanupService`（`std::jthread` + `stop_token`，随服务启动、退出时有序 join）每 2 秒轮询一次：

1. **对象异步删除**：从 `cleanup_tasks` 领取到期任务（`FOR UPDATE SKIP LOCKED`，
   多 worker 不会互相阻塞），删除前**复查 `file_versions` 的引用计数**——内容寻址意味着
   同一对象可能仍被别的文件或用户引用，计数不为 0 就跳过并标记完成。
2. **失败重试**：删除失败时记录 `last_error` 并按指数退避安排下次重试
   （1s、2s、4s…上限约 17 分钟），超过 `max_attempts`（默认 5）置为 `FAILED` 等人工处理。
   **数据库状态绝不会因为磁盘删除失败而被改成"已删除"**。
3. **回收站过期清理**：默认每 60 秒扫一次，把 `deleted_at` 超过保留期（默认 30 天，
   `TrashServiceOptions::retention_seconds`）的条目永久删除并清理对象。

设计约束：不在锁内做磁盘 IO；每条任务独立处理，单条失败不影响其他；所有后台线程可停止。

系统需要后台任务框架或最小任务调度器，至少支持以下任务：

```text
清理过期上传会话
清理孤儿临时文件
清理待永久删除对象
更新用户存储统计
清理过期分享链接
清理过期审计日志
```

在此之外，后台机制还必须能够执行：

| 任务能力 | 说明 |
|---|---|
| 过期上传会话扫描 | 扫描过期上传会话并收尾 |
| 临时分块清理 | 清理上传失败或过期后遗留的临时分块 |
| 失败对象清理 | 清理上传失败遗留的对象 |
| 回收站过期清理 | 清理已过期的回收站资源 |
| 永久删除任务 | 异步删除对象存储内容 |
| 对象存储与数据库不一致扫描 | 发现磁盘对象缺失、数据库记录缺失等不一致 |

### 3.1 Worker、队列与线程生命周期

- 实现后台 Worker。
- 实现任务队列。
- 使用 RAII 管理线程和停止流程。
- 所有后台线程必须可停止。
- 实现服务优雅退出。
- 实现 `SIGTERM` 处理。
- 服务退出时不能直接丢弃任务。
- 实现启动时恢复未完成任务。
- 不在锁内执行慢速网络或磁盘操作。
- 线程、锁与资源管理的红线见[项目根 AGENTS.md](../AGENTS.md) 第 5 节。

### 3.2 孤儿文件

孤儿文件包括：

- 磁盘中存在但数据库中没有引用的对象。
- 数据库中存在但磁盘对象不存在的记录。
- 上传失败后遗留的临时文件。
- 合并过程中服务崩溃产生的中间文件。

清理策略：

1. 先扫描并记录。
2. 等待安全观察期。
3. 再执行删除。
4. 删除失败进入重试队列。
5. 管理员可以查看清理结果。

**不得启动服务后立即删除所有“未被引用”的文件**，防止误删正在提交的数据。

对象与数据库一致性的判定规则见 [storage.md](storage.md)。

### 3.3 清理任务的硬性约束

- 清理任务必须幂等。
- 重试必须有上限。
- 失败原因必须写入日志和任务状态。
- 删除失败必须可重试，并且不阻塞 HTTP 请求。
- Redis 重启后不能导致上传状态永久丢失。
- PostgreSQL 中的上传会话是恢复依据之一。

## 4. 幂等与重试

### 4.1 幂等

| 对象 | 要求 |
|---|---|
| 恢复操作 | 必须幂等（见 1.2） |
| 清理任务 | 必须幂等（见 3.2、3.3） |
| 客户端重复请求 | 幂等操作清单、`Idempotency-Key` 约定与实现要求见 [data-model.md](data-model.md) |

### 4.2 重试与退避

- 后台任务失败后必须重试。
- 重试间隔使用指数退避。
- 必须设置最大重试次数；重试必须有上限，不得无限重试。
- 超过上限后进入死信或人工处理状态。
- 失败原因必须写入日志和任务状态。
- 永久删除失败必须可重试（见 1.3）。
- 清理阶段删除失败进入重试队列（见 3.2）。
- 网络中断场景下，达到最大重试次数后允许手动重试（见 2.1）。
- 前端重试的可重试错误清单与 500 ms / 1 s / 2 s 退避时序见 [frontend.md](frontend.md)。

## 5. 备份与恢复

备份集合至少包含：

```text
PostgreSQL 备份
文件对象目录备份
Redis 可选备份
配置和密钥备份
```

恢复顺序：

1. 恢复 PostgreSQL。
2. 恢复对象存储目录。
3. 检查数据库对象和文件对象一致性。
4. 启动 Redis。
5. 启动后端。
6. 执行完整性扫描。
7. 检查孤儿对象和缺失对象。
8. 允许用户访问。

必须说明：

- 仅备份 PostgreSQL 不能恢复文件内容。
- 仅备份文件目录不能恢复完整文件元数据。
- 数据库和对象存储必须作为一个备份集合处理。
