     权限用大白话（`PERMISSION_LABELS`：只读 / 可写）。发送成功提示：**"对方登录后在左侧
     「分享给我的」里就能看到并下载"**。

  错误统一走 `sharingErrorMessage`。

### 4.3 刷新后的恢复

前端刷新页面后，需要根据后端上传会话恢复状态，而不是只依赖内存中的 React 状态。

- 未完成上传任务的必要信息（`upload_id` 和文件基本信息）存 IndexedDB。
- 进入页面时用 `upload_id` 向后端查询真实状态。
- 后端返回的 `completed_chunks` 是过滤已完成分块的依据。

## 5. 上传算法与重试

### 5.1 上传流程

```text
选择文件
    ↓
读取文件大小和名称
    ↓
分块计算 SHA-256
    ↓
调用初始化接口
    ↓
获取 completed_chunks
    ↓
过滤已完成分块
    ↓
限制并发上传分块数量
    ↓
上传缺失分块
    ↓
查询上传状态
    ↓
调用 complete
    ↓
等待服务端校验
    ↓
刷新文件列表
```

前端不能依赖所有分块顺序上传。

### 5.2 并发上限

- `MAX_PARALLEL_CHUNKS` 默认 4（单文件内的分块并发）。
- `MAX_PARALLEL_FILES` 默认 3（**同时在传的文件数**）。后端对单账号的并发上传会话有硬上限
  （`MAX_CONCURRENT_UPLOADS_PER_USER`，默认 4，见 [deployment.md](deployment.md)），
  超出的建会话请求直接返回 `STORAGE_BUSY`。前端必须自己排队：
  - 名额是 **manager 级**的，一次选 20 个文件、或文件夹上传按子目录分批入队，共用同一个上限；
  - 排队中的任务状态是 `queued`（面板显示「排队中」），拿到名额才开始算哈希；
  - 排队期间被暂停 / 取消的任务拿到名额也不开工。
- 历史缺陷（2026-10-03 用户实测）：`enqueue` 曾把一批文件全部并发丢出去，
  一批视频里第 5 个文件起直接报「你的并发上传任务已达上限」，界面显示为「失败」。
- 分块大小、分块索引与单文件上限见 [storage.md](storage.md)。

### 5.3 伪代码

```typescript
const session = await createUpload(file);

const pendingChunks = chunks.filter(
  (chunk) => !session.completedChunks.includes(chunk.index),
);

await runWithConcurrencyLimit(
  pendingChunks,
  MAX_PARALLEL_CHUNKS,
  async (chunk) => {
    await uploadChunkWithRetry(session.uploadId, chunk);
  },
);

await completeUpload(session.uploadId);
```

### 5.4 可重试错误

```text
网络断开
连接超时
HTTP 408
HTTP 429
HTTP 502
HTTP 503
HTTP 504
STORAGE_UNAVAILABLE
STORAGE_BUSY（并发上传名额已满，等名额而不是判失败）
```

### 5.5 不可直接重试错误

```text
401
403
404
409
413
422
HASH_MISMATCH
QUOTA_EXCEEDED
```

### 5.6 重试时序

```text
第 1 次：500 ms
第 2 次：1 s
第 3 次：2 s
```

加少量随机抖动，避免大量请求同时重试。

- 自动重试只针对可重试错误，次数有上限。
- 达到上限后停止自动重试，保留会话并提供手动重试。
- 不可直接重试错误必须直接反馈给用户，不进入自动重试。
- **等名额**（`STORAGE_BUSY`）用另一张更长的退避表 `SLOT_WAIT_DELAYS_MS`
  （1 s / 2 s / 4 s / 8 s）：让出的是「别的文件传完」，比网络抖动等得久；
  等满 4 次仍拿不到名额才把错误抛给用户（状态显示「服务器同时在传的文件已满，正在排队等待…」）。
  这条兜的是「同一账号在电脑和手机 / 两个标签页同时上传」——单靠 `MAX_PARALLEL_FILES` 挡不住跨端。

## 6. 数据与 Token 处理

- 使用 TanStack Query 管理服务端数据。
- 使用 IndexedDB 保存未完成上传任务的必要信息。
- 不在 LocalStorage 中保存密码。
- 不在 LocalStorage 中保存长期敏感 Token —— **例外（用户 2026-10-03 明确要求）**：登录页的
  「记住我」勾上时，令牌写 `localStorage` 并配 30 天长效令牌（`JWT_REMEMBER_EXPIRE_SECONDS`），
  因为"手机 App 每次都要重登"是产品缺陷；不勾就仍然只进 `sessionStorage`。
  这是**显式**取舍：长期存储会放大 XSS 的后果，所以勾选框默认在、但可以取消，
  并在 `README.md`「认证与 Token 策略」写明生产环境应改 HttpOnly Cookie。
- Token 处理方式必须统一，避免多个页面分别实现。
- 刷新后从后端会话恢复状态，而不是只依赖内存中的 React 状态。
- 认证方案与 Token 生命周期见 [api.md](api.md)，Token 安全要求见 [security.md](security.md)。

## 7. 交互与质量约束

- 所有 API 错误必须展示用户可理解的消息。
- 所有破坏性操作需要确认。
- 所有按钮和菜单必须根据权限显示，但后端仍然必须校验权限。
- 页面状态与上传状态必须按第 4 节区分，不得用 loading / error 两个值糊弄。
- 不能假设分块按顺序到达；重试只对可重试错误做，并有次数上限。
- 添加前端单元测试和 Playwright 核心流程测试，清单见 [testing.md](testing.md)。

## 8. 手机端（2026-09-21，用户明确指示；阶段 ② 已按"像 App"重做）

用户原话：「手机端界面适配：仍然是桌面版布局，手机上能用但挤。**修改，我用的非常的憋屈**」；
第二次反馈：「这个手机端网页的适配非常的粗糙，感觉根本就没有设计」。
按 [AGENTS.md](../AGENTS.md) §14.1，手机上难用属于**产品缺陷**，因此这不是可选优化。

**判定**：`frontend/src/hooks/useIsMobile.ts` 统一给出「窄屏」= AntD `lg`（992px）以下。
不直接用 `Grid.useBreakpoint()` 的原因写在那个文件里：首次测量前断点是 `undefined`，
直接取反会让桌面端先闪一帧手机布局；阈值也只在那一处定义。触控最小高度用同一个文件的
`TOUCH_HEIGHT`（44px），不要在组件里各写一个数字。

| 「我的」页 `pages/MyPage.tsx` | 最近文件 / 回收站 / 设置（管理员多一项系统管理）+ 退出登录；一行一个、≥60px、整行可点 |

| 缩略图 `components/FileThumbnail.tsx`（2026-10-03） | **只有图片**才去换票据加载小图，其它类型渲染图标占位、**不发请求**（列表里几十个文件不能每个都白跑）。挂载在文件卡片（手机）与搜索结果里 |

## 9. 广场（2026-09-21，阶段 ⑤；用户明确指示）

「广场」回答两个问题：**现在谁在线**、**同一账号还有哪些设备在线**。入口是手机底部第 2 个 Tab
与桌面左侧导航（`navigation.ts` 的 `MAIN_NAV_ITEMS` / `MOBILE_TABS`，路由 `/plaza`）。

### 9.1 心跳与在线判定

- `features/presence/usePresence.ts`：登录后每 **30 秒** `POST /presence/heartbeat`；
  标签页在后台时不发（`refetchIntervalInBackground: false`），**切回前台立刻补一次**。
- `device_id` 在浏览器本地生成一次并长期复用（`localStorage` 的 `lfh.device_id`，
  只含 `[A-Za-z0-9._-]`、长度 ≤ 64，后端会校验）；`device_name` 形如 `Chrome · Windows`
  （`deviceNameFor(userAgent)` 是纯函数，有单测）。
- 服务端 **90 秒**收不到心跳即视为离线（`ttl_seconds`）；在线状态**只在服务端进程内存里**，
  不落库、重启即清空，当前按**单机单进程**假设（多实例各记各的）。
- 心跳结果放在 react-query 缓存（`presenceKeys.heartbeat`），广场页与设置页共用一份，不重复请求。

### 9.2 界面

- **谁在线**：每张卡显示用户名 + 平台标签 + 设备名，右侧是**显眼主按钮「发文件给他」**
  → 打开「选一个文件」（列「我的文件」，可按名字过滤）→ 选中即授权（只读）→
  提示"他登录后在左侧「分享给我的」里就能看到并下载"（与 §14.3 口径一致）。
  列表**不含自己**、**不含隐身用户**；同一个人多设备只出现一次。
- **我的设备**：同一账号的其它在线设备；文案明确写出 **"同一个账号的文件本来就是同一份，不需要互传"**
  （AGENTS.md §14.2），并提供「在另一台设备上打开（显示二维码）」（复用 `ShareLinkBox`）。
- **空状态**用大白话告诉用户怎么让别人出现（"让同事连上同一个 WiFi 或你的热点…"）。

### 9.3 隐私

- 默认**可见**（用户要求"只要在线就默认显示"）；「设置」页有开关，关掉后别人看不到你，
  你自己仍能看到自己的设备；切换会立刻 `PUT /presence/visibility` 并刷新缓存。
- 别人的在线信息只有"是谁 + 什么设备 + 最后活跃时间"，**不返回其它用户的 `device_id`**。

### 9.4 验收

`frontend/tests/e2e/plaza.spec.ts`（Pixel 7 视口）：底部 Tab 有「广场」且能进页面 →
「谁在线」里**不含自己** → 「我的设备」显示 §14.2 的口径 → 无横向滚动 →
在「我的 → 设置」里切换隐身开关，并断言真的发出了 `PUT /presence/visibility`（隐藏与恢复各一次，均 200）→

## 11. 手机端卡片列表与"防横向溢出"（2026-10-03，用户实测反馈）

用户原话：「现在的手机浏览器网页端还是做的太潦草了，太潦草了！！！」+
「我点击底下的导航栏，点击分享给我的，导航栏就直接消失了」。

**根因是同一个**：「分享给我的」「回收站」「系统管理」这些页面直接用了**电脑版宽表格**，
在 412px 宽的手机上表头被挤成竖排（"名 称 / 类 型 / 大 小"），而且表格比屏幕宽 →
整页横向溢出 → 横滑时 `position: fixed` 的底部导航被推出可视区（用户看到的"导航消失"）。

**规则（改手机端页面时必须遵守）**：

1. 手机上**不要用宽表格**：一条一张卡（`components/MobileItemCard.tsx`）——
   图标 + 名称 + 一行次要信息（`大小 · 权限 · 时间`）+ 一行操作，
   **主操作是整行大按钮**（高度 `TOUCH_HEIGHT`），破坏性操作用 danger 色。
   `components/FileCardList.tsx`（文件页）是同一套约定的既有实现。
2. 确实要保留表格的地方（管理员的用户/审计表）：给 `scroll={{ x: 720 }}`，
   让表格**在自己内部**横滑，⛔ 不许把整页撑宽。
3. `index.html` 里有一道兜底：`html, body { overflow-x: hidden }` + `.ant-table-wrapper { max-width: 100% }`。
   它只是保险，**不能拿它当修法**（真正的问题是页面用了不适合手机的布局）。
4. 回归钉死：`tests/e2e/mobile.spec.ts` 现在断言「切到 /shared 与 /trash 后底栏仍在可视区内」
   与「页面无横向溢出」（Pixel 7 视口）—— 这条就是用户报的 bug，不要再让它回来。

实测（2026-10-03，便携实例 + 无头浏览器 Pixel 7）：`/files /plaza /shared /recent /me /settings /trash`
七个页面**底栏全部在可视区内、横向溢出全部为 0**；「分享给我的」在有内容时渲染为卡片
（文件名 + `29 B · 只读（可查看与下载） · 2026/10/3` + `READ` 标签 + 整行「下载」主按钮）。
