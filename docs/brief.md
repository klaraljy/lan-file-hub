# lan-file-hub — 项目简报

> 状态：草案 ｜ 最后更新：2026-09-12

## 一句话

一个面向个人和中小团队的私有文件管理与局域网文件共享系统，支持用户、文件夹、文件上传下载、断点续传、
文件版本、回收站、分享链接和资源权限控制。

项目不是单纯的网盘 CRUD 应用，也不是第一阶段就实现完整 Dropbox 或 Syncthing 的分布式同步协议。
第一阶段优先交付：可通过浏览器使用的文件管理系统、大文件分块上传、网络中断后的断点续传、文件哈希校验和
去重、文件版本与回收站恢复、用户和资源权限、可通过 Docker 启动、可测试、可恢复、可部署。

> **定位（用户已确认）**：自己先用起来，但按**工业级标准**做——目标是做到**公司可以采用**的水准，
> 不是练手玩具。因此权限、审计、故障恢复、可运维性不是加分项，而是交付标准；
> `phases/` 里阶段十一～十七的可靠性、安全与部署工作属于发布前必做，不是可选项。
> 自用只是起点，不是验收标准。

## 给谁用

| 角色 | 他们做什么 | 他们得到什么 |
|---|---|---|
| 个人用户 | 在电脑和服务器之间保存文件；通过浏览器访问家庭服务器或个人 NAS；上传大文件并支持中断恢复 | 防误删；保存多个文件版本；大文件上传中断后不必重来 |
| 小型团队 | 在公司局域网中共享资料；管理项目文档和部门文件；控制用户对文件夹的读写权限；通过分享链接向外部人员提供临时访问 | 统一的团队文件入口；细粒度读写权限；可撤销、可过期的对外分享；文件操作审计记录 |
| 后端和基础设施开发者 | 学习 C++ 文件 IO；学习高并发上传下载；学习对象存储抽象；学习 PostgreSQL、Redis、权限、状态机和故障恢复 | 一套可运行、可测试、可压测的完整系统；通过压力测试证明系统性能 |

## 核心循环

> 归纳自功能清单与阶段任务书，是系统的主使用路径。

1. 用户注册或登录，进入自己的根目录。
2. 在文件夹树中浏览、创建、重命名、移动目录。
3. 上传文件：小文件直接上传；大文件切分为固定大小分块逐个上传，形成上传会话。
4. 上传中断后重新连接，按已上传分块继续，不重传已完成的分块。
5. 全部分块到齐后服务端合并、重算大小与 SHA-256，按哈希去重，对象进入最终路径。
6. 文件在事务中建立版本、更新当前版本指针；同名修改产生新版本而不是覆盖。
7. 其他用户按权限读写该资源；需要对外时创建带过期时间的只读分享链接。
8. 删除进入回收站，可恢复；确认不再需要后由后台任务永久清理。
9. 全程产生审计记录；后台任务清理过期上传会话、临时对象与回收站中超过保留期的文件。

## 为什么值得做

| 问题 | 依据 | 状态 |
|---|---|---|
| 凭什么有人用 | 传统文件共享方式存在以下问题：邮件和聊天工具不适合传输大文件；直接使用共享目录缺少权限和审计；网络中断后需要重新上传整个文件；文件覆盖后难以恢复历史版本；多个用户同时修改文件容易产生数据丢失；文件元数据和磁盘内容容易不一致；删除操作缺少回收站和恢复机制；单纯依赖前端校验无法保证安全 | 有依据 |
| 凭什么你做 | ① 自己就是用户：先解决自己真实要用的文件存储与共享，需求不是编出来的。② 目标定在「公司可采用」：私有部署、权限与审计完整、故障可恢复、可运维。现成开源方案（Nextcloud、Seafile 等）功能全但体量大、二次开发与定制成本高，本项目把取舍压在**文件传输的可靠性与可恢复性**上，并把 C++20 的资源占用与并发能力作为差异点。③ 有完整的阶段任务书与验收标准，不是边写边想 | 用户已确认定位后填入 |
| 凭什么现在做 | ① 没有外部时间窗口，属于「自己要用」，本来随时可做，不需要抢时间。② 生态成熟度：Drogon、vcpkg、CMake Presets、Docker Compose 这套组合已经把 C++ HTTP 服务与依赖服务的搭建成本压到个人可承担的范围，早些年同样的东西要先自己啃依赖与构建。③ 需求侧在变：团队内网文件共享与审计要求越来越常见，而公有网盘的合规性在多数公司过不了 | 用户已确认定位后填入 |

## 新颖点

> 归纳自原分析反复强调的几项约束；原分析没有单列「创新点」章节，这里说的是本项目的取舍重点，
> 不是宣称技术首创。

- **大文件分块上传 + 真正可恢复的断点续传**：分块默认 8 MiB，上传会话与分块状态持久化，网络中断、
  后端重启、Redis 重启后都能继续，而不是重传整个文件。
- **服务端重算哈希的去重**：合并完成后由服务端重新计算大小与 SHA-256，不信任客户端声明；
  相同内容只存一份对象，元数据各自持有引用。
- **版本与回收站**：软删除 + 恢复 + 后台永久清理；修改产生新版本而不是静默覆盖，
  并发修改以冲突响应暴露而不是丢数据。
- **权限与分享**：用户级 READ / WRITE / OWNER 权限，管理员 ADMIN；分享链接有哈希存储的 Token、
  过期时间与撤销能力。
- **故障可恢复性**：数据库与磁盘不是同一个事务系统，因此明确「先落盘、后改库」的顺序，
  失败遗留的对象交给后台清理任务；重复分块、重复完成、重复取消、重复恢复、重复删除分享都必须幂等。
- **全程流式**：单个下载连接不导致全文件进入内存，大文件上传不一次性载入内存。

## 范围

### 做（MVP 必须支持）

- 用户注册和登录；短期 JWT 鉴权。
- 文件夹创建、重命名、移动和删除。
- 文件上传、文件下载。
- 文件列表和分页。
- 文件大小、类型、创建时间、更新时间显示。
- 分块上传；断点续传。
- SHA-256 哈希校验；文件去重；配额。
- 文件版本记录。
- 回收站；文件恢复；永久删除。
- 文件夹和文件权限。
- 分享链接；分享链接过期。
- 操作日志。
- 管理员查看用户和存储统计。
- Docker Compose 启动。
- 单元测试、集成测试和端到端测试。

### 不做（非目标，不得在第一阶段阻塞主流程）

- 多节点自动同步。
- P2P 文件传输。
- 局域网节点自动发现。
- 完整的桌面同步客户端。
- S3 协议兼容。
- 在线 Office 编辑。
- 在线视频转码。
- 病毒扫描的真实引擎集成。
- 复杂的多租户计费。
- 企业单点登录。
- 分布式一致性协议。
- 端到端加密。
- AI 文件分类和语义搜索。

以上能力可以通过接口预留，但不得为了预留接口引入空泛的复杂抽象，也不得在 MVP 阶段提前引入复杂实现。

本项目**与 AI 无关**：不引入 AI 能力，不做语义搜索、智能分类或推荐，不依赖模型服务、向量库或推理框架。

### 以后可能做

上述非目标全部属于后续阶段方向；另有「客户端自动同步」「局域网节点发现」「S3 兼容存储」等能力明确属于
MVP 之后的阶段。
